## コンテキスト

「欲しい機能がなければ自分で作れ」る拡張機構では、「誰が作ったPluginか」が実質的なセキュリティ境界になる — 自作Pluginは構造上信頼でき、他者Pluginは採用判断が要る。

Pluginは好きな言語・好きなフロントエンドの任意コードとして動く。任意コードに実行時隔離を課すには、言語非依存のsandbox・権限プロキシ・資源制限が要り、設計と実装の主戦場になる。

## 決定

**A. VS Code型 — インストールしたPluginを信頼する** を採用する方向。

- Pluginはホストと同等のOS権限を持つ任意コード（VS Codeの拡張機能モデルと同じ立場。類似の前例として参照する）
- 悪意あるPluginからCoreのSecretやOS資源を保護する機構は持たない想定で進める
- 信頼判断は実行時ではなく**採用時**に行う。他者Pluginのレビュー・選択を助けるskillを整備して補う（`docs/requirements/00003`）

## 代替案

- **Sandbox型**: 権限制限・APIプロキシ・OS分離。安全だが「好きな言語・好きなフロントエンド」の自由度と両立しにくく、Protocol全般に影響する
- **権限宣言+同意UI型（ブラウザ拡張型）**: 中間案。宣言と実態の乖離を検査しない限り実効が薄く、検査するには実質sandboxが要る
- **独自配布審査型**: 公式がPluginを審査して配布する案。流通を公式に集中させ、自作・社内利用の自由を狭める

## トレードオフと帰結

- 得るもの: Plugin実装の自由度の最大化、Core・Protocolの単純さ
- 失うもの: 悪意ある・稚拙なPluginへの技術的防壁。OS上の他プロセス・他ユーザーとの分離はOSのアクセス制御依存となる
- Plugin UIのShadow DOM等は見た目の分離を目的とし、JavaScriptのセキュリティ境界とはみなさない想定で進める
- 再検討トリガー: 第三者Pluginの流通が始まり、権限モデル・分離・共有環境の要求が具体化したとき
